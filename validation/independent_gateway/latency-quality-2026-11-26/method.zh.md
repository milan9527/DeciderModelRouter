# 两阶段 Liquid 延迟优化：方法与边界

本次保留 `gpu-evidence-two-stage-public-v2`：第一次 GPU 判断七项需求，第二次 GPU 阅读全部合格配置的依据并选模。应用路由代码、模型权重、候选及公开评测快照不变。优化发生在现有 g5.xlarge / A10G 上的 Liquid 服务。

## 实现

第一阶段继续使用 BF16 eager 推理。第二阶段使用 Liquid 自带的 `model.compile()`，通过 PyTorch Inductor 减少算子调度开销。在导入 Torch 前设置 `TORCHINDUCTOR_EMULATE_PRECISION_CASTS=1`，尽量保留融合前的中间精度转换；HTTP 工作线程也检查配置。

编译在服务启动时完成：使用 92 份固定输入，加上 3 次基础初始化，总计 95 次预热。本次启动预热约 109 秒，完成后才进入就绪状态。请求遇到需要重新编译的形状时，使用同一 CUDA 模型的 eager 路径，避免在线编译造成长时间等待。每阶段仍只有 1 次实际前向计算。没有剪掉候选、删除评测、使用答案缓存或改为 CPU 选模。

代码：[Liquid 服务](../../../deployment/open_models/liquid_server.py)、[GPU 网关](../../../deployment/open_models/gateway.py)、[部署与失败回滚](../../../deployment/enable_liquid_compile.py)。部署脚本针对现有实例，保存源文件和 systemd 单元备份，上传校验、预热、实际 HTTP 推理检查通过后重启网关。脚本拒绝盲目覆盖已经带 `--compile` 的单元；升级或回滚应先核对保存的部署记录与单元内容。

## 性能实验

从固定质量测试中取出 46 次路由的 92 个真实 GPU 输入，在同一台 GPU 上轮换原版与编译版执行顺序。两组都临时暂停 H2O，并在实验后恢复；此处没有调用目标模型。报告的时间是 **Liquid 服务内的墙钟耗时**，包含分词、GPU 推理和内存清理，不是纯 CUDA kernel 时间，也不是 ECS 端到端耗时。

主比较排除启动预热；预热开销另存。报告 P50、P95、最大值与峰值显存。最终两阶段合计使用“原版第一阶段 + 编译版第二阶段”的逐输入时间之和，不能把两个阶段的独立 P95 直接相加。随后再用三个决策模型均常驻时的正式 HTTP 服务验证全部 92 份输入。

## 数值一致性与已知差异

普通编译可能改变接近的分类分数。保留精度转换后，离线两阶段全部编译仍有 2 个第一阶段属性变化，因此最终只加速第二阶段。

正式 92 份输入通过最终 HTTP 服务时，368 个决策字段全部与原版一致，其中 46 次选模一致。**另有一个 4096-token 产线预热输入从 Claude Opus 5.5 改选 MiniMax M2.1**；将已知额外用例纳入后，选模一致性为 **46/47（97.9%）**。最初汇总遗漏了这个预热输入的差异，现已单列纠正。两次额外目标调用都因 4096 上限截断，均未通过；它们不并入正式 44 项质量测试。

保留精度转换不等于保证任意输入逐位一致；上述是有限输入的一致性检查，也不等于业务正确率。

一次临时部署还发现：在主线程导入 Torch 后修改配置，不能保证 HTTP 工作线程具有相同值。该部署已回滚，最终版本改成导入前环境变量并加入线程内检查。部署、核验和最终源文件哈希另存。

## 44 项任务验收

固定套件版本 `a315fc7ed2dfb2e660699c04`，基线提交 `8d511ef6ffe7f5bce0bb4de4d2a17eff9d9aa371`。两边分别调用真实 Bedrock 目标模型：

- 通用文本与历史 13 项、12 行业业务题、复杂产线分析 1 项、代码 7 项、检索 1 项。
- 多模态 6 项：图片 4、语音转写 1、短视频描述 1。没有覆盖图像生成、视频生成、长视频、复杂音频等全部能力。
- 零售与支付对账各 2 轮原生工具 Agent，共 4 个验收项。这里运行的是本地生产适配器；另外的线上 AgentCore Runtime V2 检查单列。

输出上限 16,384 tokens，目标不重试、不回退。输入、期望答案和评分规则先冻结；参考答案与评分规则不传给 GPU 或目标模型。`new_holdout` 是建集时的标签，这 12 个新增行业输入之后也用于性能回归，最终不能再宣称独立盲测。

主指标为“完整遵循要求并完成任务 / 全部 44 项”。格式错误、内容错误、截断、调用失败、待评分、未测都不从分母剔除。“内容正确”仅作为辅助指标，允许单独说明数值或代码功能正确但格式不符，不修改原始验收失败。

代码在无网络、只读文件系统、低权限 Docker 中执行正常、边界、错误输入和输入不变性测试；围栏格式另判。明确答案自动校验，开放答案由本助手按冻结规则复核，公开输出哈希、理由和非盲评标识。视频对照实际素材帧：未要求的颜色可不写，但主动添加错误颜色或变化仍属于内容错误。

两组目标回答重新生成，未固定相同采样结果。若同一型号的回答一边正确、一边错误，不能据此断言编译改善或损害了推理能力。44 项是定向开发回归，不能取代原来的 87/159 项全量评测，不能据此证明质量统计上不下降。Wilson 区间只描述样本比例，不能消除选样偏差。

## 中断记录

优化组首次质量测试时，本地 SSM 转发已退出，44 次尝试都在得到 GPU 结果前失败，目标调用为 0。该批次原样保留在 `quality/optimized-transport-failed/`，不冒充目标模型质量结果。重新检查服务健康和实际 GPU 调用后，完整重跑优化组。服务可用性审计应同时看这批连接失败，不能只看替代批次。

## 复现

```bash
# 先建立授权的 GPU 私网转发，并实际检查模型健康及推理。
PYTHONPATH=. .venv/bin/python scripts/run_latency_quality.py \
  --output .deployment/reproduction \
  --suite validation/independent_gateway/latency-quality-2026-11-26/suite.json \
  --arm optimized

PYTHONPATH=. .venv/bin/python scripts/check_latency_code.py \
  --input .deployment/reproduction \
  --image <已审核的本地运行镜像>

# 完成独立开放题复核，按输出 SHA-256 保存 reviews.json 后：
PYTHONPATH=. .venv/bin/python scripts/summarize_latency_quality.py \
  --input .deployment/reproduction
```

套件运行器会跳过已保存尝试；重测需使用新目录并保存原因，不能覆盖失败记录。新一轮会产生真实目标调用及费用。当前 GPU 已启用优化，`--arm baseline` 只是批次标记，不能将编译服务自动还原；基线实验需要明确部署原版并记录服务状态。

## 机制

旧版先判断任务属性，再按每组6个候选逐轮淘汰。107个候选需要22次选模请求，另有1次任务判断。新版先枚举满足明确输入输出和硬约束的所有可能配置，一次GPU请求同时回答七项属性与一个目标配置。实际路由仍由GPU根据评测、费用、能力与会话信息选择。

分类前的候选并集可能大于分类后的合格集合。本次普通请求约134个配置进入GPU；不是只取质量排名靠前的模型。收到联合答案后再次检查所选配置是否满足实际任务属性，若不一致，明确不执行，不追加隐蔽的分类、排序或GPU调用。

Liquid原生多问题接口的前向调用计数实际为1。一次HTTP请求不等于所有模型都只做一次前向计算；Decider和H2O没有提供相同的计数，不能据此宣称三者GPU计算量相等。目标模型明确限流且尚无输出时，已有回退政策可以再发起一次独立选模，记录中保留总次数。

## 测量口径

GPU服务测量包括分词、模型计算和临时CUDA缓存释放，不是纯CUDA内核时间。线上联合决策时间还包括候选证据准备、GPU排队与HTTP往返。分类与选择共享这次推理，前端不再将两段时间相加。历史中的新版联合决策P50/P95与旧版选模P50/P95分别统计。Decider/H2O的Token用量可能累计多个问题，不能把请求合计直接当作单条上下文长度。

历史对照来自[上一版真实调用](../bedrock-evidence-2026-11-26/live-validation.json)，其选模时间尚未包含另一次分类。新旧样本属于相同场景的功能回归，不是相同负载下的大规模延迟实验，不能据此计算生产SLA或准确率。

## 选择依据控制实验

构造128个同能力、同价格且不带真实型号偏好的候选，只有一个代码正确率为99/100，其余20/100。交换最佳候选的位置和评测后，检查选择是否随依据改变。另用相同99/100正确率、不同价格检查低成本偏好。每项只做一次GPU请求。

最终编码使用直白的 `Coding correctness 99/100` 和 `cost=$0.001`。早期把正确率写成紧凑代码的试验未通过交换对照，未发布；不能只靠缩短提示词衡量改动是否成功。这些人工控制只验证选择对依据的敏感性，不是行业任务或全部Bedrock模型的路由准确率。

质量交换对照：Liquid **2/2**、H2O **2/2**，Decider **0/2**。Decider两次都选了首位候选，说明它在当前128候选编码下没有可靠利用这项依据；接口能接受完整候选不能当作选模质量通过。默认继续使用Liquid，Decider保留为对比选项，其联合选模效果尚未验收通过。Liquid另两项价格交换对照也通过：相同99/100正确率时，两次均选择更低费用的候选。

## 回归边界

软件回归覆盖全部候选进入GPU、单请求计数、同时返回属性与模型、答案冲突不执行、会话、回退、历史与新旧统计隔离。真实调用覆盖通用对话、连续会话、代码、图片和向量；行业Agent另测零售四轮。保留目标实际输出、调用错误和回退，不把接口完成当作业务答案正确。

历史87场景与逐型号补测报告保持原样。这次没有重跑全部行业准确率评测，也不把少量控制实验替代独立业务验收。[路由与评测说明](../../../docs/BEDROCK_CLASSIFIED_ROUTING.zh.md) · [AWS架构](../../../docs/INDEPENDENT_SERVICE.zh.md)。

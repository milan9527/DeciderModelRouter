# Liquid 选模原因诊断 · 2026-11-26

结论：当前产线案例存在明显的候选顺序／内部编码敏感性和名称敏感性。
低概率、差距小的最大项仍会被执行，网关还丢弃了原始概率分布。
不能归结为没有传入 LiveBench、简单不会比较数字、超过候选上限或本次编译加速造成选错。

这是单案例受控诊断，共25次GPU请求，不是准确率或质量验收测试。
调用现有 Liquid 服务，没有调用目标 Bedrock 模型，没有改变线上代码、权重、部署或路由策略。
所有合成和反事实成绩仅用于本地实验，未写入产品评测依据。

## 输入与运行核验

- 原始输入来自已归档 manufacturing-liquid 线上记录。
- 重建 SHA256 与线上 decision_calls 中记录完全一致：
  `f67f3df298c7687d422848921a1450ac69cfad43671a071ed14ac3e6cca7b3d5`。
- 正式候选106项配置；模型读取9583 input tokens，output tokens为0。
- instructions为4963字符；候选说明合计16884字符；state为1265字符。
- 运行 BF16；模型代码与固定版本
  `LiquidAI/d1-2B@cfe5760ff5d5998f91d9ac56bd4b2dbd96996d41` 的已归档哈希一致。
- 读取源码的 tokenizer.encode 没有截断，runner 将完整序列送入模型；
  官方模型卡上下文128K，当前请求远低于该值，未发现输入截断依据。
- 选择是答案槽概率的最大项，不生成逐步推理文本。概率不是业务答题成功率。

| 简洁匿名106选一，同批次、同成本，高分项置于0/14/53/105位置 | 四次均选高分项 |

换序同时改变了模型原生的A/B/…选项编码，因此不能将结果进一步断言为单纯的前部或尾部偏好；
可以确认的是候选排列和内部编码变化会影响当前案例。需要更广泛实验才能测量这种影响的普遍程度。

名称交换是反事实敏感性实验，不是合法的真实模型质量比较，也不能将这种实验中的模型ID当作实际名称。
名称变化影响结果，不能从中读取模型的内部推理原因。

编译和eager的概率存在小差异，两个检查输入的最大单项差约0.00258与0.00095，
但第一名均相同。因此本案例不支持“编译导致Devstral胜出”；不据此保证所有输入完全数值一致。

## 机制与限制

模型输入同时包括任务要求、模型名称、参考批次、评测档位、未知值、费用和旧请求P95。
简洁106选一可以完成，原输入甚至两选一仍然不合理，说明不能只把错误归因于候选数量。
分数0/100对照说明分数确实影响输出，也不能断言模型完全忽略LiveBench。
当前证据支持复杂输入中的权衡不稳定；没有单独隔离语言、批次、未知价格、配置差异等每一个因素。

`app/gateway_decision.py` 的选择分支只保留
`answers = {"action": {"choice": answer}}`，没有保留服务返回的confidence/probabilities。
原生模型默认取最大概率；当前多候选请求也没有额外的“不确定”选项。
因此，即便106候选下最高项仅3.84%、领先约0.58个百分点，系统仍呈现一个确定选择。
不能把3.84%当作该模型答题正确率，也不能直接与两候选下的65.8%比较。

优先改进方向：让证据字段和偏好说明更清楚，保留概率及第一二名差距用于诊断，
使用换序、匿名名称、分数扰动和跨场景验证检查真实GPU选择是否稳定。
这些方向不等于恢复旧答题评分、CPU质量淘汰门槛或额外质量GPU重选。
本次尚未实施线上修复。

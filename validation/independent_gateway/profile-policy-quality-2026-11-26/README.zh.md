# 一次需求评估 + CPU选模：全面质量测试

2026-11-26，针对实验方案 **Liquid一次GPU评估7项需求 → CPU根据评测、费用和时延选模 → 实际调用Bedrock**，完成143项计划用例的执行与复核。**整体通过69/143（48.3%）**，60项未通过、2项待复核、12项未测。速度较快，但复杂行业推理、代码和接口适配仍存在明显问题，不能据此认定可上线。

本报告只评价这版未部署实验；线上仍使用原有GPU联合决策。没有修改生产策略、写入生产评测历史或发布到前端。行业测试通过本地执行器调用项目现有原生Bedrock Agent适配器及合成数据工具，**没有经过线上AgentCore Runtime V2**。

## 通过率与分母

“通过”要求实际结果满足本轮任务：核心事实、计算、约束、代码与明确格式要求均成立。返回HTTP成功、完成生成、选中了模型，都不能单独算质量通过。缺少材料时正确澄清可以通过；3个预先登记的输入/预算边界，正确拒绝执行也可以通过。

12个会话均观察到模型切换，共23次相邻模型ID变化。典型路径为 **GPT-OSS 20B → GLM 4.7 Flash → GPT-OSS 20B**；政务交接继续使用GLM。12个代码轮次均选择GLM 4.7 Flash，但均未满足质量要求。说明“会切换”不等于“切换正确”。本轮实际缓存读取为 **0 tokens**，不能声称实现了缓存节省，也不能由此否定其他型号已有的缓存支持。

具体问题包括：

- **保险**：重复票据再次计赔、同一事故免赔额重复扣除，当前赔付14400元、补齐材料后22500元被算错。
- **法务**：50万元的30%写成150万元；将不同付款节点的验收与发票拼成“已满足付款条件”。
- **能源**：总电量5015−5000应增加15 kWh，回答反复写215 kWh，错误继续进入第4轮摘要。
- **制造**：已有3个实验组合，却声称再补1批即可补齐8组；把拟隔离写成“已隔离”。
- **电信**：用户分钟115000计算正确，却把跨站用户总和定义为独立人数；交接将“超过30分钟”改为“≥30分钟”。
- **政务**：漏扣补件暂停时间，错判超时件数，进而从3条记录外推28件积压中的超时比例。
- **代码**：制造、物流、SaaS、电信的Python代码块存在确定的语法错误；其他轮次有分货库存来源错误、冲突判断反转、未定义变量、参数次序不符、仅返回输入而不使用暂停区间等问题。能源代码轮次没有提供代码，转而提出不必要的澄清。
- **交接格式**：教育排程的主要内容正确，但明确要求三条，实际只有两条，仍属本轮未通过。它与计算错误分别说明。

行业代码采用语法检查及源码静态复核；没有把语法通过当成功能通过，也没有声称实际运行了全部行业代码或验证并发正确性。

## 基础代码、多模态和新诊断

三个基础Python题要求“只输出函数，不要围栏”。三个回答均加了围栏，原始输出格式验收0/3；只剥离围栏、不修改函数后，功能测试全部通过：

| 函数 | 功能检查 | 原始格式 |
|---|---:|---|
| 顺序去重 `unique` | 103/103 | 未通过 |
| 括号校验 `valid` | 108/108 | 未通过 |
| 区间合并 `merge` | 105/105 | 未通过 |
| 合计 | **316/316** | **0/3通过** |

因此这3题不应描述为算法都错了。新增复杂区间题则不同：附带的3个实现分别仅通过10/105、69/105、69/105检查，存在修改输入和将有间隔的闭区间合并的问题。CAS题的解释与SQL版本参数不一致。新增成本比较题虽正确要求补充成功率，全文两处成本公式却互相冲突；双语题的翻译准确，但额外编造了关闭账户必然冻结或删除余额、记录的规则。另4题（去重核算、受约束排程、数据内提示注入、长历史纠正）通过。

测试代码在无网络、无凭据、只读、非root、128MB内存且限时的临时Docker容器中运行。代码来源及容器摘要保存在[原始格式检查](code-results.json)、[提取函数检查](code-content-results.json)、[新增区间诊断](fresh-code-results.json)。

| 多模态项目 | 实测结论 |
|---|---|
| 单图颜色、OCR、柱状图比较 | 4/4通过，实际附图调用 |
| 两张图顺序识别 | 1/1通过 |
| 短视频主体与变化 | 1/1通过，人工式助手视觉复核实际抽帧；不是长视频时间定位指标 |
| 英语语音转写 | 1/1通过 |

图片编辑和文生图被CPU策略选到了`stability.stable-image-search-recolor-v1:0`，但对应候选没有可执行的操作适配器。当前建池逻辑可能用汇总的图片能力覆盖具体操作不支持的排除理由，执行器最终拒绝。该问题在目标RPC前发生，属于真实路由与执行集成问题；测试中没有修复它以改变结果。

中文语音的[实际WAV](artifacts/tts-zh-0.wav)、[第一份ASR记录](media-reviews/tts-zh.json)、[第二份ASR记录](media-reviews/tts-zh-secondary-asr.json)已保留，需具备中文能力的听审/校准转写器继续核验。另一个待复核项为相关性解释：核心判断正确，但扩展了未经核对的历史类比和绝对文献断言，本轮没有外部检索依据确认全文。

向量检索采用12篇双语文档和4条跨语言查询，3个路由用例都选中Cohere multilingual v3，Recall@1、Recall@3、nDCG@3均为1.0。三个用例复用了同一组查询，不能算12个独立问题，更不能代表大规模检索。另2个文档重排题通过。

## 选模依据为什么仍不够

本轮冻结的策略文件SHA-256为`00aa0ef758ae4f03121c4d9d00a874f03f48a1f4e991bac1d2d76d8edd07b437`，策略版本`profile-cpu-policy-experiment-v1`；完整候选、证据、配置及每次选择理由均保存，没有测试到一半修改模型白名单或评分参数。

问题有三层：

1. **需求判断偏弱**。例如制造业复杂代码被评为`moderate`、更强模型收益`low`；支付并发题被分到客服用途。一次前向可以同时输出多项属性，但不保证属性预测准确。
2. **开发评测粒度不足**。制造业代码选择GLM时，依据是3/3内容通过、1/3严格格式通过的小样本；多个强弱模型都有相同的3/3，Wilson下界同为约0.4385，质量门槛无法区分复杂业务能力。随后按价格选择，40个候选落入同一个质量带。不能把3题通过外推为复杂代码可靠。
3. **实际输出还需校验**。带历史会保留正确事实，也会延续前轮错误；模型能调用工具，不表示它正确使用了金额、去重和约束。单纯增加输出token没有解决这些问题，长答案反而出现更多互相矛盾的附加实现与事实。

167次路由中，162次选出型号、5次无候选。GPT-OSS 20B被选123次（包括2次Agent协议失败），GLM 4.7 Flash为14次，其余25次分布于8个型号。这里是**选中次数**，包括被执行器阻止的2次图片操作；完整型号分布见[summary.json](summary.json)，不能当作各型号独立质量排行榜。

157个目标执行观测中，143个有参考价格，已知参考费用合计约 **0.04053美元**。其余价格未知，不能补零或计算完整的单次成功成本。这个数字不含独立评审、补充ASR、GPU/基础设施或失败请求费用，不是本次测试AWS账单。三个检索观测各包含16次向量调用；157不是底层RPC总数。

最终有24项与原始模型评审状态不同：20项从通过改为未通过、2项从未通过改为通过、1项从通过改为待复核、1项从待复核改为通过（视频视觉复核）。详见[修正记录](review-corrections.json)及[助手复核](assistant-audits.json)。例如：

- 评审器发现能源215 kWh错误却仍输出`pass`，最终纠正。

- 物流首轮正文已写出K1/K3须SLA核查，不能只因未放进主表判失败，最终改通过。

## 未测项与执行修正

12个预登记未测项为：实时搜索、真实业务数据库、真实外发动作、超长文档、PDF、电子表格、音画同步、实时双向语音、多人说话人分离、长视频时间定位、压力测试、故障注入。实时搜索遵循用户不启用的约束；真实DB和真实外发动作没有被合成行业工具冒充。

原87套件中的多轮记忆、多图和检索补上了真实输入及答案标注；严格JSON Schema用实际约束选模。普通排序JSON被错误推断成需要原生Schema支持而无候选，单独算路由未通过。3项预设边界仅为缺图片、零预算、空允许列表，中文TTS和生成能力缺口不作为正确拦截通过。

最初6个媒体用例因本地执行器遗漏`runtime.user`属性，在媒体解析/目标请求前失败。修复执行器后只重做这6项，旧记录保存于[harness-invalid](harness-invalid)，额外6次GPU判断不混入167次正式观测。这是测试设施修正，不是删除目标模型失败。后续5轮依赖恢复的初始记录另存[dependency-initial](dependency-initial)。

输出上限16384 tokens，遵守各端点已核验的较低上限；本轮无记录为`incomplete`的最终输出。没有因限流、质量差或延迟高重试目标模型。预登记基础套件中的压力测试缺口说明沿用了“顺序执行”文字，本执行器实际使用最多2个并发工作槽；它仍未做专门压力测试。

## 建议的改进与复现

保留一次GPU需求评估的架构，优先修复以下问题后再复测：

1. 将操作适配器和原生工具协议作为强约束；普通JSON格式要求与provider原生Schema保证分开。
2. 用复杂代码、行业计算、真假事实、跨轮约束等数据细分评测；使用独立保留集校准需求属性及选模质量，不再仅靠3题同分后比价格。
3. 在测试流程中增加确定性金额/约束校验与代码执行，将格式、事实、函数正确性、工具协议分别记录；对评审模型的判定做交叉验证。
4. 建立配对实验，在相同143题和新保留集上比较当前线上方案、需求评估+CPU策略、强模型参考，测量质量差异与每个成功任务的完整成本。当前结果没有证明相对哪种方案更优。

本次只增加隔离评测工具、记录和文档。路由、目标适配器、线上历史和部署配置均未改动。

复现需要Python 3.12（Sonic SDK）、项目依赖、AWS Bedrock权限、现有GPU隧道以及相应Secret Manager读取权限。新增目录运行会再次产生Bedrock费用。先启动现有GPU的端口转发，再执行：

```bash

python -m scripts.review_profile_quality --input .deployment/profile-quality-new
```

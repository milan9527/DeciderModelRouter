# 五模型业务流程对比

[打开模块](https://d3i7ogfx5ml7dc.cloudfront.net/#comparison) · [English](FIVE_MODELS.en.md)

同页比较 **Strands Decider、Liquid d1-2B、H2O-Lightning 4B、Jev、GPT 6.1 Sol low effort**。重点看每个模型用了多长时间做决策，以及执行后的业务状态是否达到任务目标。

三个本地模型已常驻同一台 **g6.xlarge / L4**，单并发依次运行，不再逐次卸载、切换权重。五列从同一初始任务开始，各自运行完整流程；后续输入包含各模型自己的实际执行结果。

## 场景与操作

| 分类 | 业务场景 | 展开步骤 | 最终验收 |
| --- | --- | --- | --- |
| 支付客服 | USDC 到账、补款、退款、商户结算，共 4 条 | 客服受理 → 付款核验 → 风控审批 → 资金处理 → 回复结案 | 模拟资金处理完成、工单结案 |
| 模型路由 | 客服、代码、结算分析、双语索引，共 4 条 | 识别流程 → 选择模型 → 实际执行下游任务 | 流程符合任务类型、目标模型返回完整结果 |
| 设备控制 | 回家开空调、降低温度并保持其他设置，共 2 条 | 设置电源 → 设置温度 → 设置模式 | 三个实际设备状态字段符合要求 |
| 常用温度 | 替换常用温度范围，1 条 | 识别替换/新增/清空 → 选择并保存温度 → 读取结果确认 | 集合恰好为 22、23、24、25°C，且模型确认完成 |

共 **11 条流程，每条 3–5 步**。选择业务场景、检查共同任务后点击“开始五模型流程对比”。顶部五列显示累计决策耗时、工具执行耗时、流程耗时、实际目标检查及最终结果。下方点击步骤，逐列查看真实输入、候选、模型返回和执行记录。支持编辑任务、反转候选顺序和导出整轮 JSON。

支付使用模拟订单、账本与工单，设备使用模拟状态，不连接真实钱包或设备。支付样例的资金、确认数与审批等初始条件已满足执行要求，测试模型是否真正执行和结案。未执行资金处理就选择结案会被执行保护拦下；页面同时保留原始选择和实际动作。不会由程序替模型补选、改写错误温度或重试到成功。

路由保持原始两步决策：模型先选择流程，再依据候选的公开评测证据选择具体型号，并实际调用该型号。没有程序替选排名第一的型号，也没有目标调用失败后自动换型号。**路由的基础验收不代表生成内容全部正确或所选型号必然最优**，可直接核对展示的目标结果。

温度范围使用统一的 15 个二选一问题（16–30°C），每个模型都回答相同问题，不使用某一家专有的多选接口。设置动作会真正改变保存集合：如果误选“新增”，旧温度仍会保留，最终验收会发现多余值。修改任务后不再沿用样例参考与目标评分，保留执行状态供人工核对。

## 部署与计时

| 模型 | 当前运行方式 |
| --- | --- |
| Strands Decider v19 | vLLM 0.31.0，BF16；沿用已有 `:8100/v1/systemone` |
| Liquid d1-2B | 官方 Transformers `system_one`，BF16 |
| H2O-Lightning 4B v1.4.1 | 官方 shim + 补丁 vLLM 0.30.0，在线 FP8 |
| Jev | System One，`jev-latest`，现有 IAM Lambda 转发 |
| GPT 6.1 Sol | Bedrock Converse，`us.openai.gpt-6.1-sol`，low effort |

三本地模型位于 `us-east-1` 的现有按需 `i-0ae7eb0abcb815af3`，4 vCPU、16 GiB 主存、单 L4。12 次真实 GPU 烟测全部成功，烟测后总显存 **19,147 / 23,034 MiB**，主存约 4.9 GiB 可用，无 swap。本次未新增实例；图片和原版/SFT 服务仍位于另一台现有 GPU。

Liquid/H2O 与 Decider 的依赖环境隔离。H2O FP8 与此前独占 GPU 的 BF16 配置不同，旧性能和质量分数不能直接沿用。精确模型来源、版本及哈希见 [models.json](../validation/open_decision_models/models.json)，没有再次微调。配置、systemd 启动顺序和私网端口见[维护说明](../deployment/open_models/README.zh.md)。

- **每步决策耗时**：ECS 后端提交推理到收到完整模型响应。包含私网或云 API 往返；Jev 包含 Lambda 转发。
- **累计决策耗时**：各步骤 `timings.processing_ms` 的精确求和。15 问题的温度集合仍算一个模型请求，不能直接与单问题耗时当作同负载比较。
- **工具执行**：模拟状态更新或实际 Bedrock 目标调用，单独累计，不计入决策耗时。
- **本模型流程**：从轮到这个模型开始到该模型结束，不包含等待其他模型的时间。
- **本轮总等待**：五个模型依次处理的整轮墙钟时间。

单并发用于观察决策速度和业务行为，不是吞吐压测。Decider 当前引擎/活动问题并发均为 1，HTTP 准入 32；Liquid/H2O 每模型并发 1。三个本地模型持续驻留，但其他模块或公共 vLLM 请求仍可能影响共享 GPU 延迟。模型自报耗时与使用量保留在原始输出中，不替代后端计时。

## 比较口径与接口

模型收到 `state` 和 `questions`，参考答案只用于离线对照，不发给模型。相同初始状态下，一旦选择或执行不同，后续请求随各自业务状态变化；导出记录包含每步完整输入及指纹，不能假设所有后续输入仍逐字相同。“步骤选择符合参考”“已执行步骤数”“实际任务目标”分别展示，互不替代。

GPT 用统一提示词返回候选 ID JSON，没有受约束解码。无效 JSON、超时和目标调用错误按真实失败保留，不静默修复；失败后的依赖步骤停止，其他模型继续。

| 应用接口 | 作用 |
| --- | --- |
| `GET /api/comparison/catalog` | `workflow-v2` 场景、初始任务与步骤、五模型列表 |
| `POST /api/comparison/runs` | 提交 `case_id`、可选 `task`、`variant`，立即返回运行 ID |
| `GET /api/comparison/runs/{id}` | 查询各模型步骤、实际结果和计时 |

沿用现有登录、CSRF 和账号隔离。当前单 API 进程全站只运行一轮，冲突返回 409；最多保留 20 条记录，每条 30 分钟。重启清除内存记录，刷新页面仅恢复查询，不重复提交请求。私有 S3 + CloudFront OAC 和 ECS 架构保留。

本批值得对照的行为：

- **支付**：Decider 完成四条资金处理与结案；Liquid 完成三条，在已结算案例误判超时并升级；H2O/Jev 在到账和补款样例选择等待，未入账。部分受理或核验选择与参考不同，但最终完成结果另按实际状态检查。
- **设备**：对“26°C 降低 2°C，其他不变”，Decider 设为 18°C 且切换制冷，Liquid 设为 20°C；H2O、Jev、GPT 最终保存了正确状态。模型执行错误没有被程序改成 24°C。
- **路由**：五个模型在四场景的流程分类均正确，具体选型仍不同。代码任务中 Decider/Liquid 所选目标约 40 秒读取超时，H2O/Jev/GPT 所选 Claude Sonnet 5.5 达到 4096 输出 token 上限，五条业务目标均未完成。结算分析只有 GPT 路由到 GPT-6.1 Sol 后返回完整结果；其他四侧所选目标超时。整批 20 次目标调用含 7 次超时、3 次 token 截断；这些不是决策 API 失败。
- **多温度**：五个模型均完成替换、保存与确认。Decider/H2O 的 15 问题步骤比单问题慢；Liquid 在本次多问题请求中最快。

三个本地模型在本配置下都能快速给出有效决策，但各自仍有业务选择错误。Decider 的支付流程表现较好；H2O 在相对温度控制中达到目标；Liquid 的本批平均决策耗时最低。选择模型时应同时核对具体任务的执行结果，不能只看响应是否成功。
